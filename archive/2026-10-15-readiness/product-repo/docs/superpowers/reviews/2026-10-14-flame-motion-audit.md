# Flame scene and motion source audit — 2026-10-14

Scope: read-only implementation audit requested for an app-composed OS. Only this report was written. CLAUDE.md was read; codegraph was used first, followed by direct reads of omitted source. No implementation changed, no tests executed, no Aspire/runtime/UI verification performed. All behavior below is source-verified or explicitly proposed; it is not proof of runtime operation. The implementation examined is **Flame**, not a demonstrated Flare/Rive runtime. No separate Flare claim is justified by this audit.

## Conclusion

C# synapses can author scene definitions, transforms, tweens, and restricted behavior-tree data through a durable scene neuron. Flutter/Flame renders that data and reports input. This is a useful finite declarative platform, not an unlimited app renderer. New node types or tree operations need installed C#/Dart contract and renderer support. Unknown node types being accepted and displayed as placeholders is forward compatibility, not extensibility that renders arbitrary functionality.

Moving app-specific composition and reaction logic into C# is achievable within the installed vocabulary. Keeping animation ticks, hit testing, accessibility integration, asset decoding, and gesture recognition local is necessary for a useful generic connector. Requiring every animation frame to be controlled remotely by a C# synapse is neither the current architecture nor a sensible prerequisite for app ownership. The boundary should be app-owned declarative policy and durable state versus generic local execution and temporary interaction state.

## Verified contracts and ownership

Paths below are repository-relative, with one-based source lines.

- `src/DigitalBrain.Modules/DigitalBrain/Flame/DigitalBrain.Modules.Flame.Contracts/Scene/SceneDefinition.cs:5-30`: Transform has x/y/z, scale, rotation, opacity. Tween has property/from/to/duration/curve/repeat. SceneNode has id/type/style/parameters/children/tweens/inputs/optional tree. Camera has x/y/zoom. State has revision and full definition. There is no arbitrary renderer executable or arbitrary shader contract in this shape.
- `src/DigitalBrain.Modules/DigitalBrain/Flame/DigitalBrain.Modules.Flame/Scene/SceneNeuron.cs:13-20`: Set checks writer, validates definition, rejects stale expected revision, and durably saves SceneChanged. `:24-34` reports SceneInput without changing scene revision. `:36` Read does not invoke SceneAccess locally; do not infer a complete cross-brain read vulnerability without reviewing framework admission.
- `src/DigitalBrain.Modules/DigitalBrain/Flame/DigitalBrain.Modules.Flame/SceneAccess.cs:8-31`: brain space and app scene keys have distinct ownership. Platform is admitted; user/assistant must match brain; app must match brain and owning app and cannot write space. Unstamped in-silo calls are admitted. This prevents simply making an ordinary app the current space writer without an intentional ownership design change.
- `src/DigitalBrain.Modules/DigitalBrain/Flame/DigitalBrain.Modules.Flame/FlameEndpoints.cs:15-29`: brain-scoped GET scene and POST report bridge shell and neuron. Scene keys are URI-unescaped. Input facts carry name/nodeId/kind/x/y/payload (`...Contracts/Scene/Signals/SceneSignals.cs:8-10`).
- `src/DigitalBrain.Modules/DigitalBrain/Flame/DigitalBrain.Modules.Flame.Contracts/FlameVocabulary.cs:5-13`: limits are 4,096 scene nodes, 64 KiB parameter key/value bytes, 256 tree nodes, depth 16. These are limits, not demonstrated performance budgets.

## Actual renderer capabilities

- `src/DigitalBrain.Modules/Google/Flutter/app/ui/lib/src/flame/node_components.dart:212-225`: fixed switch supports circle, rect, text, sprite, path, particles, group, activity_ring, sphere. No dynamic registration/loading mechanism appears here. `scene_game.dart:64-68` substitutes PlaceholderNode for unknown types.
- `.../node_components.dart:61-85,95-153`: signature comparison avoids restarting unchanged nodes; transforms and tweens execute locally. Tween effects cover x/y/scale/opacity/rotation. Repeat is infinite alternating animation. Both x/y become full MoveEffect targets, so simultaneous independent axis tweens need a dedicated interference test.
- `.../primitive_nodes.dart:45-70`: text is canvas text, left-to-right, not an editable rich-text control. `:113-159` path parser is a restricted move/line/close list, not general SVG path support. `:73-110` sprite uses Flame.images.load; the sphere's authenticated icon loader is a separate path.
- `.../prefabs/sphere.dart:206-269`: sphere loader guards asynchronous results by generation, disposes replaced images/pictures/codecs, renders SVG into 96x96 image, loads first raster codec frame, and wakes game after arrival. This does not implement arbitrary animated image playback.
- `.../scene_game.dart:55-133`: scene refresh diffs ids, reconstructs changed types, reparents retained children, removes missing nodes, applies camera/background. Full definitions are walked; this is not a server patch protocol.

## Behavior trees: declarative but deliberately closed

- `...Flame.Contracts/Scene/BehaviorTree.cs:5-36`: nine kinds: selector, sequence, repeat, condition, wait, moveTo, scale, fade, pulse. Conditions compare string-valued blackboard keys. Sequence optionally remembers running child. This is a visual behavior DSL, not general C# execution in Flutter.
- `...Flame.Contracts/FlameSchema.cs:25-32,51-92`: checks shape, count/depth, declared/reserved condition keys and task ranges. Wait max 60 s; move/scale/fade/pulse max 10 s; positions +/-4096; scale .1–4; fade/pulse 0–1.
- `.../ui/lib/src/flame/behavior/tree_runtime.dart:28-71`: closed kind dispatch builds local tree nodes; unknown kinds fail; interrupted tasks restart their clock. `:96-135` memory sequence execution is local.
- `.../ui/lib/src/flame/prefabs/sphere.dart:182-189,303-319`: only the sphere component in the inspected palette attaches HasBehaviorTree and builds the tree. Base NodeComponent stores treeDef but does not execute it. Thus attaching a valid tree to a circle/rect is not evidence that it runs.
- `.../ui/lib/src/flame/behavior/default_idle_tree.dart:5-29`: running/attention pulse amplitudes and durations are hardcoded in Dart. `sphere.dart:115-175,303-313` hardcodes sphere colors, badge, label layout and unready opacity. These are policy currently owned by renderer, contrary to a literal all-UI-policy-in-C# goal. Decide which should become theme/presentation data versus generic defaults.

## Concrete blockers and correctness gaps

1. **Reduced motion is partial.** `scene_view.dart:59-67` observes MediaQuery.disableAnimations. `scene_game.dart:136-159` stops entrance effects and passes preference only to spheres. Generic tween creation (`node_components.dart:116-152`) ignores the preference; particle generation (`primitive_nodes.dart:175-199`) also ignores it. SphereVisual.begin suppresses new effects (`sphere.dart:78-79`), but setter only flips a bool (`:284-285`) and does not cancel existing body effects. Existing descendant effects can continue to tick. Need preference changes during each effect type tested, with defined snap/retain policy, and particle disable behavior.
2. **Advertised input and runtime differ.** FlameSchema declares tap/drag/hover (`FlameSchema.cs:18`); inspected NodeComponent mixes TapCallbacks and DragCallbacks (`node_components.dart:31-32`) and implements tap and drag only (`:169-209`). No hover handler appears in this renderer base. Treat hover as unproven/unsupported until explicitly implemented and tested. Keyboard focus/semantic actions are not represented by this scene contract; SceneView uses autofocus:false (`scene_view.dart:143-147`).
3. **Input reports are not validated against declarations.** SceneNeuron.Report (`SceneNeuron.cs:24-34`) checks nonempty identifiers, access and node existence but not that kind is a known gesture or present in node.Inputs, nor finite coordinate/payload bounds. A caller with report access can send arbitrary kind for an existing node. Require declared gesture enforcement, input payload contract and limits, and tests for forged/obsolete node input. The meaning of coordinates is inconsistent: tap reports localPosition (`node_components.dart:172`); drag reports component position and comma-delimited velocity (`:195-201`). Specify coordinate frames and typed drag payload before general gesture composition.
4. **Schema/render fidelity is not assured by schema parity.** Rect schema exposes corner (`FlameSchema.cs:38`) while renderer reads radius (`primitive_nodes.dart:37`); caller-provided radius is rejected as unknown by SceneValidation (`SceneValidation.cs:38-42`). Path renderer reads fill/stroke (`primitive_nodes.dart:124-128`) but path schema exposes only d (`FlameSchema.cs:41`). Text align is accepted (`:39`) but not applied in TextNode's TextPainter (`primitive_nodes.dart:52-58`). Numeric/color parameters also need rendered-output tests rather than assuming schema acceptance means visible behavior.
5. **Validation budgets leave cost holes.** SceneValidation (`SceneValidation.cs:16-27`) counts nodes and parameter bytes; it does not bound scene nesting separately, tween counts, overall serialized bytes, transform/camera finiteness, particle counts or numeric magnitudes. Numeric parameters only parse a double (`:67-75`). Unknown node types return early from schema checks (`:34-37`), bypassing gesture/tween checks too. Tree bounds are stronger than generic scene bounds. Define budgets and adversarial validation before treating app bundles as safely renderable.
6. **Refresh/event delivery needs hardening.** SceneView starts an async read per refresh (`scene_view.dart:87-109`), accepts any differing revision rather than monotonic newer revision and has no per-request generation guard when scene/client changes (`:71-84`). Out-of-order completion can plausibly apply stale scene data; this is source-derived risk, not reproduced. Report errors are swallowed (`:129-133`). Define recoverable input failure feedback and test stale responses, switching scene, reconnect and concurrent updates.

## Performance and accessibility implications

`scene_game.dart:170-182` pauses after three idle frames and wakes on input/apply/assets, which is a useful optimization. Every live frame scans descendants for effects, particles and spheres needing frames. Any ParticlesNode keeps the loop live. Sphere needsFrames (`sphere.dart:287-294`) treats any custom tree as active even if it is only a wait/false condition; reduced motion stops that flag but does not stop the generic Effect/Particles tests. Scene updates traverse the full hierarchy and compute signatures including JSON trees. Benchmark scene count, tree count, active effects, asset decoding and updates under realistic device budgets; 4,096 allowed nodes is not proof of 60 fps.

Canvas-drawn controls need accessible names/roles/states, keyboard and switch actions, focus order, text scaling, high contrast, and assistive hit regions. The examined scene node shape does not supply these semantics and SceneView does not create a semantics tree. Flutter widget composition may supply other accessible surfaces; this audit does not claim the whole shell lacks accessibility. Require scene-specific parity before moving primary app controls to Flame.

## Proposed boundary and acceptance work (not implemented)

- App C# owns scene composition, declared semantic actions, explicit motion policy/targets, blackboard facts and durable outcomes. Generic local connector owns frame interpolation, pointer tracking, cancellation, scroll/drag physics, rendering, focus and accessibility adapters.
- Formalize versioned renderer capabilities (supported nodes/params/tree tasks/input/motion/asset types) and publish/install validation against target capabilities. Placeholder fallback should clearly mean unsupported rendering, not successful app support.
- Put app-specific sphere defaults/theme/entrance policy into data where intended; retain documented generic fallback. Allow visual behaviors on all intended node kinds or explicitly reject trees on others.
- Keep platform trust/permission policy in host contracts. Space app authoring requires a scoped authority mechanism; do not weaken scene writer checks to achieve composition.
- Add render-contract tests for every accepted field, plus C#/Dart/JSON parity tests. Existing `ui/test/flame/node_schema_test.dart` compares schema metadata; metadata equality alone misses corner/radius, align, and ignored trees.
- Add tests for all motion modes on every node, live preference toggle, zero duration, simultaneous tweens, interruption, scene replacement, reparenting, drag reconciliation, hover/keyboard accessibility, rejected undeclared reports, response reordering, bounded pathological inputs and asset lifecycle.
- Existing test locations include `src/DigitalBrain.Modules/DigitalBrain/Flame/tests/DigitalBrain.Modules.Flame.Tests/Scene/` and `src/DigitalBrain.Modules/Google/Flutter/app/ui/test/flame/{scene_game_test,sphere_test,sphere_assets_test,tree_runtime_test,prefabs_test,node_schema_test}.dart`. Presence is source evidence only; no pass status claimed.
- Completion evidence must include appropriate C# module and Dart ui/shell checks, healthy Aspire runtime, real scene Set/Read/Report via digitalbrain-mcp and correlated trace/log evidence. Actual animation/accessibility/performance must also be observed on target rendering devices; reading neuron state cannot prove a visual frame budget or screen-reader usability.

This platform can support many app experiences through an expanding shared vocabulary. Neither C# being general purpose nor unknown scene types being accepted proves that every possible UI/application can run without extending the connector.
