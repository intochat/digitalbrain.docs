## Redesign (2026-10-12): the scene boundary is typed by a schema
Context: the brain-as-data complexity review (`docs/superpowers/reviews/2026-10-12-brain-as-data-complexity.md`, part 9) found one load-bearing smell — `SceneNode.Type:string` + `Parameters:Dictionary<string,string>` interpreted by a Dart switch with no validator, so a C# writer and the Dart reader can disagree silently. Proposal `docs/superpowers/specs/2026-10-12-flame-redesign-proposal.md`; plan `docs/superpowers/plans/2026-10-12-flame-redesign.md`. The user chose **Option A** (schema-validated data nodes), **S2** (one stage-key resolver), and unknown node **types** stay placeholders.
- Ruling F11: the scene vocabulary is one schema (`FlameSchema`, in the Flame contracts); `SceneValidation.Check` enforces it at `Set` — a known type's parameters must be declared, required ones present, values valid (number/color/JSON/choice), gestures and tween property/curve in the vocabulary — while an **unknown node type is still accepted** (an older shell renders a placeholder, Review Focus 4). The canonical artifact `docs/superpowers/contracts/flame-schema.json` is read by a C# fact (`SchemaParityFacts`) and mirrored by Dart `node_schema.dart` (a `flutter test`), so a schema change must update the artifact and both mirrors or tests fail — cost if wrong: a known-type parameter change is a two-language, artifact-touching edit (that is the point); the Dart runtime `orElse: idle` fallback remains, but drift is caught by the parity tests rather than silently.
- Ruling F12 (S2): the stage's owner form is one contract constant (`StageKey.ForOwner`), the module owns both forms in one resolver (`StageNeuron.KeyFor`), and `FlameEndpoints`/`Ino`/`BrainView` call them instead of hardcoding `/stage/owner` — cost if wrong: none (behaviour unchanged; the alias and digest are the same strings).
