# Local operation and deployment boundaries

The product entry point is `dotnet run intochat-os.cs` from the product repository. The launcher starts the Aspire AppHost. Read the selected profile and deployment configuration before starting it; a profile's name does not certify production readiness.

## Current prerequisites

- SDK version from product `global.json`: .NET 11 RC with roll-forward configuration.
- Infrastructure and native prerequisites required by the selected AppHost profile, including container services and the Flutter desktop shell when enabled.
- Required storage custody and identity settings.
- Credentials for selected model/providers when those capabilities are used.

AppHost currently selects RunProfile.Cloud. Local and Reference profiles also exist. Do not copy older Gemma-only or distributed-mesh instructions from archived docs.

## Run IntoChat OS locally

The `local` profile runs a lean module set against a host Ollama, with no cloud account and no provider credentials.

Prerequisites: the .NET SDK from `global.json`, Docker Desktop in Linux containers mode (or Docker Engine), and Ollama installed and running on the host (`http://localhost:11434`).

```
dotnet run intochat-os.cs preflight   # check the machine, change nothing
dotnet run intochat-os.cs local       # preflight, pull the model, start the AppHost
```

`preflight` checks the .NET SDK, Docker reachability and Linux container mode, Ollama reachability, free ports (including Windows excluded port ranges), disk and memory, and optional GPU and Flutter. Hard failures stop `local` with exit code 1 and a `fix:` line; soft findings (no GPU, no Flutter) are reported and the run continues.

`local` pulls the model as a visible step, then starts only the floor modules (ai, apps, circles, flame, tools, csharp, orleans, aspire, mcp) plus Azurite and the C# sandbox. Postgres, Qdrant, ClickHouse, Supabase, GitHub, Playwright and the other optional modules are disabled. The sandbox image is built from source on first run (about 30 to 60 seconds).

### Choosing the model

The default model is `qwen3.5:4b`. On a low-RAM machine use a smaller one:

```
dotnet run intochat-os.cs local --model qwen3.5:2b
```

or set the configuration key `IntoChatOS:Local:Model`. The GPU flag `IntoChatOS:Local:Gpu` only applies to a container Ollama and is set from preflight detection.

### Headless chat

A usable chat is one model turn through the neuron surface; the Flutter desktop shell is optional. Against the MCP front (`http://localhost:5081/mcp`, loopback only) call the tool `neurons_call` with:

```
{ "contract": "IntoChat.OS.AI.Models.ILLM",
  "key": "default",
  "method": "Generate",
  "arguments": "[{\"messages\":[{\"role\":\"user\",\"content\":[{\"$content\":\"text\",\"text\":\"Say hello.\"}]}]}]" }
```

The arguments string is a JSON array holding one `InferenceRequest` (web casing); the exact shape is exercised by `LocalChatTurnFacts` in the product repository. The result is an `InferenceResult` whose messages carry the assistant text generated by the Ollama model. There is no plain HTTP chat route on the kernel.

### Reset

```
dotnet run intochat-os.cs reset --list   # print what would be deleted
dotnet run intochat-os.cs reset          # print the list, type yes to delete
```

Reset runs only in the Development environment in run mode. It removes the repository `.intochat-os` workdir, the `%LOCALAPPDATA%\IntoChatOS
untime` directory, this checkout's Aspire containers and volumes, and the shared `intochat-os-csharp-cache` volume (shared by every checkout). Secrets (the user-secrets master key) and the machine-id are kept unless you pass `--include-secrets` or `--include-machine-id`. Non-interactive runs need `--yes`.

### Windows notes

- Docker Desktop with the WSL2 backend: raise the WSL2 memory limit in `.wslconfig` if the model and containers do not fit.
- In Git Bash set `MSYS_NO_PATHCONV=1` before Docker commands with container paths.
- Hyper-V and WSL can reserve port ranges; preflight reports ports inside an excluded range.

## State and access

The runtime owns an encrypted local brain journal. Account/platform data, identity protection and application database state have their own storage responsibilities. Recovery requires the matching stores and keys; preserving only the features folder is insufficient.

Local run mode defaults to Open authentication posture unless configured otherwise. Public use requires an explicitly secured deployment and acceptance at its actual origin.

Customer Researcher's historical successful browser run used an authenticated desktop on the runtime machine. That does not demonstrate remote browser automation for a browser-only visitor.

This product assessment did not start, stop or reconfigure the user's product runtime. See [Requirements](product/requirements.md) for deployment acceptance.

Names changed in os 0.3.0: see the [release notes](./reference/releases/os-0.3.0).
